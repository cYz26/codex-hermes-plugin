# 自进化定期审查方案

方案更新于 2026-11-13。前两周每天审查前一自然日的自进化过程，交付一份日报。每周深评作为后续扩展。

由 Codex 每天整理证据并给出一份报告，用户先用 3–5 分钟阅读摘要，再按需查看产物差异和来源。每日集中看新增、变化、异常和未关闭问题，Hermes 继续承担既有后台学习。前两周积累趋势后再评估是否调整审查深度，日报频率不会自动降低。

审查要回答四个问题：应该学习的内容有没有进入流程；学到的结论是否有根据；保存的位置、范围和形式是否合适；后续任务是否实际用到了这些经验，并产生可观察的效果。产物数量和复盘完成次数仅作为运行指标。

## 日报的时间与范围

建议每天北京时间 09:30 整理。本机全局学习配置所覆盖的项目纳入日报，标题和文件名使用受审日期。例如 11 月 13 日出报，主窗口为北京时间 11 月 12 日 00:00 至 11 月 13 日 00:00，右端点归入下一天。首页同时注明证据采样时间、覆盖项目和缺口。第一份附当前版本、待审队列和产物目录作为基线。

采集、复盘终态、审批和发布各按有证据的发生时间归属。昨日触发的复盘若今晨才完成，昨日的案例补上截至采样时的结果，今晨的完成事件计入下一期。历史问题沿用原编号。日报以本地 Markdown 保存，建议在学习 home 下的 `audits/daily/` 按 `YYYY-MM-DD.md` 留档，提供固定的 `latest.md` 阅读入口。

2026-11-13 补充：报告完成或失败后，按用户授权通过本聊天消息队列推送摘要与报告链接，忙时排队；入队结果与实际显示分别记录。逐次明细按“当时任务／纠正 → 实际沉淀对象与内容 → 原始差异 → 执行和产物状态”组织，名称链接到详情。待审提案展示拟修改原文，未保存的历史内容保持未知，流程投影不冒充业务正文。

2026-11-12 交付修正：每日 09:30 触发后先发布可读状态和异常摘要，再用已采集的紧凑证据限时补充详细审查。写作上限为 10 分钟；失败、超时或中断时报告明确写出未完成范围和原因，保留逐次台账及未决事项，不把执行状态停留在 running。最新发布索引与最后完成审查的截止点分别维护。报告写作不重复扫描全部历史，深查项目进入后续队列。

| 部分 | 整理内容 | 呈现形式 |
| --- | --- | --- |
| 整体判断 | 运行状态、最值得关注的变化、覆盖项目与证据缺口 | 一句话结论与最多 3 项发现 |
| 学习过程 | 回合采集与准入、意图触发、复盘终态和重试、产物操作结果，重点看待审、拒绝、失败和其他未闭环案例 | 首页列阶段计数，尝试和证据可在台账展开 |
| 流程机制 | 版本与配置变化、重复复盘、重试、归属、发布和淘汰是否合理 | 事实、影响、判断；没有变化则简写 |
| 沉淀产物 | 新增或变更的记忆与技能，检查正确性、适用范围、重复和时效 | 产物／项目／版本／变化／结论／理由与证据表 |
| 实际应用 | 经验在后续任务中是否采用、改变了什么、验证结果；可比运行开销 | 具体案例，明确未知效果与缺失数据 |
| 待办与建议 | 需处理问题、前次进展、推荐下一步、需要用户决定的提案 | 最多 3 个优先动作，沿用稳定问题 ID |

全文通常为 1000–1800 中文字，重要产物差异可展开。产物质量使用“可用／需修订／不宜保留／证据不足”四类结论。事实、推断、建议和已完成修正分别标明；重要结论附原始来源、对象版本或采样时间。没有新增时照常生成简报并更新未决项，不重复堆叠旧内容。

日报任务以只读取证和成报为范围。记忆提案通过原生审批入口按版本处理，问题修复沿用对应的执行流程。

### 逐次状态与异常优先

用户于 2026-11-11 明确要求优先发现和审查待审批、被拒绝、未通过及其他问题。日报的“学习过程”固定包含“逐次学习状态”和“异常与未闭环案例”，完整明细另存为可点击的台账。

- 每次尝试同时列**执行状态**和**产物状态**：完成／失败／中断／等待／运行中／未知，以及已生效／待审批／被拒绝／结果未知；技能发布另查。一次执行完成可能仍含待审批和被拒绝的操作，不能统一标成学习成功。
- 记录 `attempt_id`、`intent_id`、根意图、项目、触发与来源、对象／版本、原始原因、当前处理状态、证据和下一步。触发数按根意图计，复盘次数按尝试计。产物表列写入操作数与发生变化的对象数，并链接版本差异。历史待审批结果关联当前提案及原生处理记录，原失败记录链接后续恢复结果。
- 所有已发现的异常或未闭环案例进入台账和审查队列，优先于成功产物抽样。相同原因可分组，但成员 ID 不丢失；摘要最多突出 3 项，完整问题列表不受该限制。
- 审查结论区分正常保护／合理拒绝、材料或权限不足、疑似误拒、执行故障、待核实，并注明发生在资料准入、模型执行、工具写入、人工审批或发布阶段。待审批不直接等于故障；拒绝也不自动意味着需要放宽限制。
- 跨日追踪直到有证据表明已处理，或经有依据的审查确认属于合理结果。没有结束的过程标注“截至采样时的当前状态”；没有记录的原因、时间或结果明确写未知。
- 状态摘要仅显示最近 10 次尝试。日报基于保留的原生尝试与 bridge 回执，补充重试、审批处理和当前发布决定。记录保留范围、实际枚举数量和采样时间。缺失时间的尝试记录为发生日期未知，附首次观察时间与状态变化。已清理的记录、缺失的历史发布过程和无法读取的来源进入覆盖缺口。

只读采集使用已有学习记录，不实例化原生运行时，不修改学习数据库，也不生成新的学习尝试。企业边界有效时才读取获准的必要内容，沿用现有凭据过滤。完整台账证明列出了保留的尝试，语义审查是否覆盖每个异常仍须在日报中单独报告。

## 1. 完整方案的范围与后续节奏

| 时点 | 审查范围 | 交付 |
| --- | --- | --- |
| 首次基线 | 全局登记项目、运行版本与策略、现有记忆和技能目录、待审队列、证据缺口 | 一份基线、优先问题清单；不把累计计数当作当日产量 |
| 第 1–14 天，每天 | 全局状态扫描；各项目新增或变更产物；失败、待审及上次问题；实际应用样本 | 一页日报、可展开的差异与来源、需要用户决定的具体事项 |
| 第 7、14 天 | 整条机制、全库目录、重复与过期趋势、收益与开销 | 周评：保留什么、修正什么、哪些仍需观察 |
| 稳定后 | 每日自动扫描，人工审查可降到每周 2–3 次；每周整体检查继续 | 异常仍及时呈现，不等待周评 |
| 机制变更后 | 触发规则、资料策略、写入保护、发布检查、Curator、存储或原生版本有实质变化 | 增加一次专项审查，并恢复连续 3 个有活动日的观察 |

前两周先保持每日单份报告。无新增时交付简报，写明当日活动、仍在跟踪的问题和可用证据。

第 14 天根据问题关闭情况、变更可追溯性、产物审查结果和独立任务应用证据决定后续频率。可用的初始参照为连续 7 个有活动日无未关闭的高优先级问题，以及最近至少 10 项产物审查中可用项达到 90% 且无关键事实错误。缺少适用任务时，应用效果标为“证据不足”。

## 2. 每天看什么

| 层次 | 每日检查 | 合理的判断依据 |
| --- | --- | --- |
| 采集与归属 | 新完成回合是否进入事件箱；正文准入或拒收原因；真实 cwd、项目和 worktree；中断、迟到结果 | 有任务却无采集需要调查；无活动、明确排除、凭据过滤与故障分别计数 |
| 触发与执行 | 阈值、闲时及高价值信号是否合理触发；队列年龄；失败、重试、unknown；部分写入 | 原始尝试与重试关联；旧失败被新结果覆盖需要证据；无新增经验可以是合理结果 |
| 记忆与技能 | 新增、修订、删除、归档的版本差异；来源与适用范围；是否重复、过长或过时 | 每条结论能回到原始依据；项目事实留在项目；技能具有可复用的方法和明确边界 |
| 待审与发布 | 同一旧记忆的多个提案、过期提案；候选拒绝原因；当前发布版本和验证版本 | 批准绑定看过的 revision；候选、已写入、待批准、已发布分别呈现；旧版本仍服务时明确标注 |
| 召回与应用 | 相关经验是否被找到；无关经验是否干扰；是否实际采用；验证和失败是否关联正确版本 | 推荐、加载、采用、任务验证通过分别记录；加载本身不证明复用收益 |
| 机制与开销 | 插件与原生版本、配置差异、升级检查、Curator 和留存；调用量、延迟、可用的 Token 数据 | Curator 维护以运行记录为据，技能账本提供逐项差异；费用缺失时写未知 |

### 人工 review 顺序

1. **先读首页，3–5 分钟。** 看采集与积压、待审、失败／重试、拒绝和未发布原因，定位影响最大的 1–3 项。
2. **打开需要判断的差异。** 核对原始依据、版本和项目范围。待审记忆按提案与 revision 选择批准、丢弃或暂缓。没有决定的项带入下一天。
3. **抽查一条完整链路。** 从一次用户纠正或失败恢复追到产物和后续任务，记录具体采用动作及其验证。日报给出问题的下一步和关闭证据，有异常时可用 15–20 分钟展开核对。

### 产物怎么抽查

- 初次建立完整目录，按来源、项目、类型、版本和是否可执行分类；历史正文分批阅读，覆盖未完成前只称“已审样本”。
- 前两周，当天新增／变更产物不超过 20 项时逐项检查。超过时，已有记忆的修订／删除、可执行资源、跨项目共享范围变化、有冲突或应用失败的项目全部优先审查，普通产物至少抽 5 项。
- 普通抽样同时覆盖不同项目、来源、产物类型和失败案例；样本按日期及产物 ID 固定，避免只挑成功案例。可用量不足时全部检查。
- 每天至少追踪 1 个端到端案例；有记录时覆盖“拒收、未触发、无产出或失败”的案例。无合适案例记为无样本。
- 每周回看至少 3 项旧产物，优先选长期未使用、反复改写和被新版本覆盖的内容。没有使用机会不等于没有价值。

### 判断一项产物是否合理

| 维度 | 核对问题 | 常见处理方向 |
| --- | --- | --- |
| 正确与可追溯 | 原始材料是否支持结论？是否把方案、推断、助手自述写成已经发生的事实？ | 补证据、收窄表述，无法支持则提出撤回建议 |
| 放置与范围 | 是长期偏好、项目决定、暂时状态，还是通用操作方法？适用宿主、版本和企业范围是否保留？ | 项目事实留项目；短期状态加时效；不将一次任务结论改成全局规则 |
| 可操作与边界 | 有触发条件、步骤、前提、例外和验证方式吗？命令是否能由当前接口支持？ | 补适用条件；过宽的方法拆分或缩小入口 |
| 简洁与增量 | 是否只是复述聊天、常识或既有指导？新增内容是否值得每次注入？ | 去重、合并或删减；不以技能变长作为进化目标 |
| 新鲜与一致 | 同一事实是否有相互竞争的版本？原依据或工具是否已经变化？ | 明确最新依据、过期状态及迁移关系 |
| 可验证与有用 | 结构检查、脚本检查、实际采用、任务验证分别有什么证据？ | 标注已覆盖的层级；安排后续真实任务观察 |

每项给出“可用／需修订／不宜保留／证据不足”之一，并附一条理由和来源。结构检查通过不直接等于“可用”；涉及关键事实错误或范围错误时，不能用其他维度得分抵消。

## 3. 每周整体 review

沿着“采集 → 归一化 → 触发 → 原生复盘 → 写入／待审 → 发布 → 召回 → 应用 → 整理淘汰”重走真实案例，重点检查：

1. **输入是否保真。** 原始目标、纠正、失败和最终验证之间的关联有没有在裁剪或合并时丢失；实际传入的证据与日志摘要是否一致。
2. **触发是否值得。** 高价值纠正是否遗漏；微小回合是否反复产生低价值内容；失败重试是否保留已有写入且不制造重复。按复盘根意图统计，重试不算独立学习成果。
3. **写入与发布是否合适。** 增补、修订和删除是否遵守原生保护；Curator 的合并、归档是否损失约束或证据；正文和可执行资源是否使用匹配版本的检查。
4. **知识库是否更易用。** 技能数量、正文体积、同义重复、过宽入口、过时项目记忆和未处理提案是否持续增长；广泛召回是否挤占当前任务上下文。
5. **应用是否有收益。** 选有适用机会的独立后续任务，看采用了哪条规则、改变了哪一步、是否避免重犯或减少返工。必要时用隔离的固定案例作对照，生产中不故意省略已知正确做法。
6. **演进是否可恢复。** 核对实际激活版本、候选检查、迁移与回退范围。离线测试、真实 provider、实际 App hooks 和用户界面证据分别报告；只在相关变更或异常需要时运行专项验证。

每周只提出证据最充分的 1–3 项机制改进，写清预期改善、可能代价和验收方式。需要重设计的升级沿用维护方案确认流程。

## 4. 指标口径与预警

| 指标 | 统计口径 | 初始处理规则 |
| --- | --- | --- |
| 采集／复盘覆盖 | 明确时间范围内，可采集的已完成回合与实际接收回合；满足触发条件的证据与终态结果 | 缺少独立宿主分母时写“仅学习侧可见”，不报告全量覆盖率 |
| 队列与恢复 | 未处理项数、最老年龄；按根意图分组的等待／成功／失败／unknown；部分写入数 | 连续两次日报无进展，或最老项超过 24 小时，调查原因；运行中的合法任务另列 |
| 待审负担 | 按项目列待审、同源冲突、重复、过期和最老年龄 | 超过 48 小时仍无处理意见，进入用户决策清单 |
| 产物质量 | 已审数量／应审数量；四类结论分布；缺来源、错误和重复的具体项 | 关键事实或范围错误立即列为高优先级；样本质量不外推全库 |
| 实际应用 | 有适用机会的任务样本数；推荐／加载／采用／验证／失败；精确技能版本 | 日报审查和合成探针单列；无验证记录写未知，不能写效果 0 或效果已提升 |
| 开销与收益 | 同一计数域的 API／Token 增量、耗时，以及形成可用经验或减少返工的案例 | 前 3 天建立基线；可比活动量下开销连续两天超过基线 2 倍才提出调查，不自动改预算 |

以上小时数和倍数是建议的审查阈值，不是现有服务配置，也不会据此自动删除、重试或停服务。单次健康状态不掩盖产物错误；无变化、无适用机会、未覆盖和失败分别表达。

统计实现要求：

- 用上次成功采集的位置读取增量，用北京时间自然日汇总。保存事件、版本与尝试标识以去重。补报按各自然日窗口出具，迟到终态引用原案例及首次归属日，并更新仍在跟踪的事项。
- 每个来源记录采样时间、版本和覆盖范围。累计快照与前次比较只表示可比计数差；重置、清理或迁移后重建基线，不用负差值表示负产量。
- 有上限的最近列表必须标明上限、是否分页完整；无时间或关联 ID 的历史列表只作为诊断线索。当前 `capture_coverage_gaps` 最多保留 100 项，不能据此算当日拒收率。
- 日报审查读取技能也可能生成交付回执。审查 chat／turn 和合成验证需要单独标识；当前无法精确排除时，加载量只作原始计数，不能成为业务效果指标。
- 同一原始事件的复盘、日报和周评不是三份独立证据。审查意见保持“建议”状态，下一轮必须回到原始事件与新验证；审查报告不能作为自身结论的独立佐证。

## 5. 每日交付与问题闭环

日报首页保持一页，先给出结论、变化和需要决定的内容。每项判断可展开到版本差异、原始依据、审查理由；避免要求用户从长日志里找结论。

```text
受审日期／时区：
主窗口／取证时点／运行版本：
覆盖：登记项目 __；已检查 __；未覆盖 __（原因）；采样 __ / 应审 __
结论：正常／需关注／需处理／证据不足

链路：采集与消费 __ → 准入与触发 __ → 复盘完成／失败／重试 __ → 写入／待审／拒绝 __ → 发布 __
产物变化：记忆 +__ / 改__；技能 +__ / 改__；归档__
关键发现（最多 3 项）：事实 → 影响 → 证据 → 建议
产物审查：名称、版本、项目、结论、来源／差异链接
应用案例：任务 → 使用的规则和版本 → 实际动作 → 验证 → 仍未知的效果
运行与开销：当前异常、最老积压、重试终态、可比计数增量

需要用户决定：问题 ID、对象／revision、完整差异、推荐动作和理由
跨日追踪：原报告日／问题 ID、截至采样时的结果、下一步或关闭证据
未覆盖：缺失来源、截断列表、没有样本、无法核算的指标
```

问题按“发现 → 核实证据 → 决定 → 修正 → 验证 → 关闭”跟踪。每项保存稳定 ID、对象版本、影响、下一步和关闭证据；跨日继续引用同一项。

- 凭据泄露、越范围内容或会导致错误操作的经验：立即报告并停止在当前任务中采用，提供具体修正／隔离方案；全局处置按相应维护授权执行。
- 错误结论、冲突、持续积压或重要学习遗漏：当日给出处理建议；记忆提案由用户针对具体版本决定后走原生批准／丢弃入口。
- 冗长、轻微重复、低频召回等优化项：进入周评。修改后检查新版本、发布与召回；涉及行为的问题还需独立任务或适当回归证据才能关闭。

审查本身不直接改学习数据库、已发布快照、全局指导或业务项目；不把“需要修订”的审查标签当作已经完成修复。一次处理完成后重新读取，防止后台学习期间版本变化导致判断失效。

## 6. 现有能力与落地顺序

2026-11-14：新增只读增量导出与独立完成记录，使用方式和实施门槛见
[Hermes 原生优先优化](./NATIVE-FIRST-OPTIMIZATION.zh-CN.md)。导出成功只表示证据采集；
连续真实日报、自然任务效果和通知实际显示仍单独验收。

2026-11-13 的运行快照显示，本机以全局采集范围运行 Learning 0.10.2 和 Hermes v0.23.1。每份日报取证时重新读取运行版本与范围。

| 证据入口 | 能支持的判断 | 边界 |
| --- | --- | --- |
| `learning_status(cwd, chat, turn, limit, after_cursor)` | 全局概览，按项目、聊天与回合核对采集、准入、复盘、发布和应用进度，按游标枚举保留回合 | 最近尝试摘要有上限；费用空值表示未知 |
| `bridge review-metrics --date DATE --timezone Asia/Shanghai --cwd PROJECT` | 按受审日汇总有回执的复盘用量、耗时和写入对象，可用聊天 ID 标注审查与验收 | 其余聊天保留在其他组，旧回执的通知间隔单独标注 |
| 学习 home 的 `bridge/bridge.sqlite` 与 `learning/journal.sqlite` | 只读关联采集、复盘开始／结果回执、原生尝试、重试与发布记录，补齐日报台账 | 按实际保留范围和有据时间汇总，记录缺口 |
| 原生 Curator 状态与 `skills/.curator_ledger.jsonl` | 核对维护运行、技能变更、合并与归档的来源和版本 | Curator 执行次数取自运行记录；账本统计技能操作 |
| `update_status()` | 更新策略、最近检查、候选、激活／回退状态 | 历史错误和当前状态需结合时间与事务判断 |
| `pending_reviews(cwd, id?)` | 项目范围的待审列表、差异、revision 和处理记录 | 只查询；用户明确决定后才走 CLI 的版本绑定操作 |
| `context(cwd, query)` | 当前项目记忆、共享技能目录和相关候选 | 项目范围必须显式传入；召回目录不是已应用证据 |
| `skill_load(name, cwd)` | 当前正文、资源、来源、版本及验证记录 | 留下交付记录；加载后的版本可能与先前目录不同，审查绑定实际读取版本 |
| 当前安装包的 `bridge doctor` | 配置与已有运行证据的补充检查 | 不启动模型探针；CLI 参数先核对当前帮助 |

每日版本变化清单、Curator 变更账目、跨日关联和完整日报仍需分别整理与验收。使用 `review-metrics` 时附上已标注的聊天范围和指标覆盖情况。

建议按三个步骤落地：

1. **先跑通人工基线和前三次日报。** 固定审查模板、样本和结论口径，记录现有入口可取得的证据和缺口。用户可用“按方案出昨天的自进化日报”发起。
2. **再自动整理证据。** 增加独立的只读采集与版本比较，输出结构化摘要、产物差异和待审清单。复用原生读取接口；缺少接口时评估新增只读导出，不用直接写库补齐状态。保持现有串行学习 worker。
3. **接入每日调度与阅读入口。** 确定采用调度后，在实际宿主核验北京时间 09:30 的触发与成报。按受审日期去重，失败后从上次成功的采集位置恢复，缺失日期各自补报。报告落在本地受控目录。

长期建议将报告放在学习 home 下独立的 `audits/`，与知识发布库分离；方案可版本管理，运行报告、完整证据和企业产物保持在受控位置。只保存判断必要的正文片段与来源，不复制凭据和整段无关聊天。首次实施时确定报告留存周期；关闭问题的最小证据随问题记录保留。

落地验收包括：有活动、无活动、服务离线、重试后恢复、部分写入、待审冲突、版本在审查时变化、列表截断、重复调度和迟到结果；每个场景的报告均正确标注事实与未知。另验收两次连续真实日报以及至少一个独立后续任务中的应用追踪。日报生成成功只证明审查流程能运行，学习收益需要持续观察。
